## 测什么

通过当前 AIPod Python 的 `generate_source()` / `call_llm()`，修复真实仓库
`src/actunit/runtime.py` 中的默认参数丢失、普通 handler 异常外泄、非法返回值导致崩溃。

验收测试在生成项目外提前固定，并记录内容哈希；没有在结果出来后放宽测试。

这是已有代码的修复实验，覆盖新源码生成通道，不是全库五层架构迁移或完整 CLI 建站实验。

默认重试的源码请求过程是：8,192 token 达到长度上限，然后提高到 16,384，
后两次请求均出现 APITimeoutError。请求超时配置为 120 秒。
三轮逻辑生成均成功取得 JSON 元数据，但均未取得完整 XML 源码；没有进入候选代码写入和修复后验收阶段。
最后另行运行了全部 37 项测试，确认结果仍为原有 12 项通过、独立验收 13 项通过和 12 项失败。

前两轮人为关闭内部重试用于单独观察失败。第三轮使用正式组件生成器相同的默认重试配置，
保留全部前序失败，不能把不同配置的试验混作同一组成功率统计。

## 判断

这次没有证明 Python XML-like 生成链路能稳定完成真实项目修复。
可以确认不完整响应被拒绝，指定文件及其他跟踪文件未被修改，验收文件内容哈希也未变化。
这些是失败处理的正确行为，不等于业务修复成功。

没有得到可供审查的源码补丁，也没有将人工修改算成模型结果。
当前证据仅能归因到源码响应被截断或请求超时，不能断定 XML 协议本身是根因；
尚未在这个真实任务上与 JSON 源码输出、其他模型或其他端点做同条件对照。
后续应记录模型推理/输出用量并定位预算和超时，再使用同一份验收重跑。
