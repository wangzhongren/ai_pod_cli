# FlaskBB 连续维护对照结果

这轮没有证明 AIPod 降低了维护成本。三组最终都通过了“规范化字段值＋分组限制＋失败回调”的补充验收，而 AIPod 新默认流程使用了更多请求和时间。它保住了现有结构检查，但前两轮未在各自的 180 次请求内完成最终交付。

按用户最新要求，Python 和 Node 的工作历史已改为 **160,000 字符触发 AI 压缩、320,000 字符硬上限**。Python 全量 319 项、Node 全量 91 项测试通过。一次真实模型压缩将 175,151 字符降到 17,864 字符，保留最近 3 轮原始记录并保存压缩前历史；人工核对了摘要中的需求、权限、契约、已做修改及未完成工作。

## 严格验收的歧义

AIPod 三轮的同一项失败是：规范化后的验证回调和失败回调收到字段值相等、但不是同一个 Python 实例的对象。原测试用了 `is` 断言。文字需求只明确规定“不需要规范化时保留原对象”；对新建规范化对象是否必须复用，没有写得足够明确。

因此保留全部原始严格评分，另外只把这一个断言换成五个字段值一致，其他断言不变。运行结束后，三组均通过这份 26 项补充验收。没有把补充结果反馈给 Agent，也没有用它覆盖原评分。这个失败不能单独作为“业务需求没有实现”的确定证据；复用同一对象仍是值得保留的插件兼容性约束。详见 [标准审计](CRITERION-NOTE.md)。

## 可以确认的机制

迁移代码交给 mini 后，第一轮漏改 `ValidateRegistration` 的 `envelope` 输出声明；第二轮 Provider 又直接导入了 `modules/services/impl/validators.py`。业务测试仍全绿，而 AIPod 的结构检查能识别这两类不一致。**结构门禁确有作用，但这不证明必须靠多 Agent 才能获得它。** 本轮没有测试“单 Agent＋同一套强制门禁”。

现有检查也不等于论文中的完整治理。AIPod 新策略生成的 `modules/services/impl/group_guard.py` 通过旧项目的 `Group.get(...)` 查询数据库，现有结构检查没有报错。这里仍有 legacy/`any` 边界，不能声称所有基础设施访问都受严格分层约束。

旧 80,000 字符策略在第 95 次请求时仍没有业务文件修改，且早期读取记录已从历史中被移除。新策略这一轮第 35 次请求开始写代码。不过新策略三轮业务运行中，**没有任何一层达到 160,000 字符并触发压缩**；真实压缩另用了旧历史进行一次只读功能检查。因此不能把这次提前写代码全部归因于 AI 摘要，也不能排除模型采样差异。它证明新机制可运行，尚未证明压缩带来稳定的维护收益。

旧策略停滞首先发生在首个 Service Agent，不能简单解释成多 Agent 交接成本。新策略则确实进入了多个层，重复检查、文档修改后的重新验收和最终 Pod 交付仍产生了明显开销。

## 范围与复现

使用公开 [FlaskBB](https://github.com/flaskbb/flaskbb/tree/28e0214460ff641cb1c3f56baf96dea395b7e9ab) 的固定提交，130 个 Python 源文件、454 项原有测试。只迁移注册与校验领域，其他论坛模块保留为 legacy；迁移涉及 35 个文件（包含空包初始化、配置和说明），增加 420 行、删除 148 行。迁移由实验者完成，未计量自动迁移 Agent 的成本，所以不是完整采用成本评估。

对手是官方 [mini-SWE-agent 2.4.6](https://github.com/SWE-agent/mini-swe-agent/tree/04d809ceab9df28f9adaed044884180159172930)，使用原生 DefaultAgent、官方 mini.yaml 提示词和 bash function calling；没有套 AIPod 的文本指令协议。模型均为配置的 `deepseek-v4-flash`，使用同一端点和输出上限。两个框架原生消息保留方式也不同：mini 请求中保留 reasoning_content，AIPod 工作历史保留操作文本和结果。这是默认工程流程比较，不能单独归因于 Agent 数量。

首次试跑发现 mini 能读取 `/tmp` 中预检留下的验收日志，因此三组全部作废、停止并归档。随后阻断其他临时工作区、验收日志和用户目录的内容读取，并验证两种执行环境均通过原有回归，才从干净基线重跑。原有缺失的 gettext 编译产物用上游构建命令补齐；没有改动原测试。旧 AIPod 在用户要求更新策略时于第 179 次请求停止，停止后的严格验收 8/8、原有回归全过、结构检查通过，最终交付未完成；没有伪记为第 180 次预算耗尽。

这仍是一个真实仓库中的单领域、三轮、单次运行试点，没有证明跨业务长期维护的统计优势，也没有验证任意位置崩溃后的正确恢复；Node 端只做了实现和全量回归，没有跑这份 FlaskBB 对照。
