# 订单修改实测 — 2026-09-07

测试代码基线：`2ab399c`。模型配置名称：`deepseek-v4-flash`。
使用项目现有 OpenAI-compatible 端点，全部业务数据为合成数据，没有真实订单、库存或消息发送。

## 结论

契约类型接口和依赖范围机制在本次测试中表现符合预期，但原始代码的真实模型修改流程尚未跑通。
原始版本的 6 次尝试全部在生成前失败。测试请求加入 JSON 提示后的 1 次诊断实验完成了修改，
通过全部独立业务验收，并保留无关源码。诊断结果不能算作原始版本成功，也不足以证明普遍成功率。

## 原始版本发现的两个阻断点

1. 客户端启用 `response_format: json_object`，但 `CLASSIFY_REVISION_STAGE` 的提示词没有包含 JSON 一词。
   配置端点返回 HTTP 500，错误体明确说明是 JSON 模式的请求校验错误，而不是业务执行失败。
   三次自动修改分别在约 0.201、0.107、0.178 秒失败，各调用模型一次。
2. 三次 services 规划均返回 `src/services/price-order.ts`，而规划器只接受 `price-order.ts`。
   三次分别在约 68.934、79.829、84.643 秒失败，各调用模型一次，没有进入生成阶段。
   第一份返回还把 inputs/outputs 都置为空对象；由于路径校验已先拒绝，该契约退化没有落盘。

这 6 次失败均未实现新增满减规则。修改后的独立验收只通过 7/10：原有行为仍正常，
但 10000、10001、20000 分这三个需要满减的用例失败。不能把“未改文件”算成有效的局部修改收益。

## 诊断实验

仅通过测试包装器，为每次模型请求补上一句 `Return a strict JSON object.`，没有修改生产客户端。

- 5 次模型调用，Agent 执行约 175.636 秒（不含随后独立业务验收）。
- 分类正确返回 `services / PriceOrder`。
- 范围为 PriceOrder → price → priceCli；三份对应源码发生变化。
- Order、StockMemory、ReserveStock、NotifyOrder，以及库存和通知的 Pipeline/Interface 源码哈希保持不变。
- 新生成的 PriceOrder 使用 `context.typed()`、`ctx.get()`、`ctx.output()`，没有出现 `any`。
- 0、9999、10000、10001、20000 分依次得到 0、9999、9000、9001、19000 分。
- 库存扣减、库存不足不扣减、剩余库存继续扣减，以及通知消息内容均通过验收。

调用次数不是 token 费用。本实验没有得到 token 用量，不能给出费用下降结论。
原始对照没有成功完成，诊断仅有一次，所以也不能给出速度或成功率提升百分比。

## 下一步应修复

- 在公共模型客户端统一确保 JSON 模式请求带有明确 JSON 指令。
- 对安全、符合当前阶段的项目相对路径做规范化，或提供明确的规划格式反馈重试。
- 修改已有组件时保留原有契约，并明确检查契约变更；不能只靠模型遵守“保持不变”的描述。
- 修复后，以完全相同的验收和项目基线重新跑三轮对照。
